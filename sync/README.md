# sync

The Go binary that pulls Linear issues and Slack threads, writes them to
Neo4j via the parameterised Cypher in `../data-model/queries/`, runs the
explicit linking pass that creates `:DISCUSSED_IN` edges between issues
and threads, and — when an embedding service is configured — embeds
every issue and message and runs the semantic linking pass on top (see
[Embedding and semantic linking](#embedding-and-semantic-linking)).

## When this runs

For a one-shot refresh, run this once before a demo session. It takes
seconds to minutes depending on volume — a typical demo project with
~30 issues and ~50 threads finishes in under a minute.

For the **live "watch it get incorporated" demo** — post to Slack or
create a Linear issue during the talk and have the graph pick it up
without a manual step — run with `--watch`. See
[Live demo mode](#live-demo-mode).

For a production deployment, you'd either:

- Run this on a schedule (EventBridge → Lambda invoking the same orchestrator
  with the same parameters); or
- Wire it to webhooks from Linear and Slack so changes propagate as they
  happen.

For NODES, schedule (or `--watch`, its demo-friendly cousin) is plenty.

## Layout

```
sync/
├── README.md                              # you are here
├── go.mod
├── go.sum                                 # generated by `go mod tidy`
├── cmd/
│   └── sync/
│       └── main.go                        # CLI entry point, --watch loop
└── internal/
    ├── linear/
    │   └── client.go                      # GraphQL client for Linear
    ├── slack/
    │   └── client.go                      # bulk pulling from Slack Web API
    ├── graph/
    │   └── writer.go                      # Neo4j writer, loads Cypher from disk
    ├── embed/
    │   └── client.go                      # OpenAI-compatible /v1/embeddings client (LM Studio)
    └── orchestrator/
        └── orchestrator.go                # ties pull → upsert → link → embed + semantic-link together
```

`internal/slack/` is intentionally separate from `slack-subgraph/internal/slack/`.
The subgraph plugin serves individual GraphQL queries on demand; this sync
client does bulk pulling with different pagination, rate-limit, and user
resolution concerns. Sharing code would force one shape to fit both.

## Why the Cypher lives in `data-model/queries/`

The Go writer reads `upsert-issue.cypher`, `upsert-thread.cypher`, and
`link-explicit.cypher` from disk at startup rather than embedding them in
Go. Single source of truth: edit the Cypher in one place, both `cypher-shell`
runs and the Go pipeline pick up the change. The trade-off is a runtime
dependency on the queries directory — handled via `QUERIES_DIR` env var,
defaults to a relative path from `cmd/sync`.

## Prerequisites

- A free-tier Linear workspace with at least one project containing seeded issues
- A free-tier Slack workspace with at least one channel containing seeded messages
- A free-tier Neo4j AuraDB instance with `schema.cypher` already loaded
- Go 1.23+

## Setting up credentials

### Linear

Settings → API → Personal API Keys → Create. Copy the key. It looks like
`lin_api_xxxxx`.

### Slack

Use the same Slack app you set up for the subgraph plugin. The bot token
scopes you need for sync are a superset of what the plugin needs at runtime:

- `channels:read` and `channels:history` — public channels
- `groups:read` and `groups:history` — private channels (if you use them)
- `users:read` — resolve user IDs to names
- `users:read.email` — get email addresses for Person-node reconciliation
- `search:read` — only needed if you add search-based sync later

Copy the bot user OAuth token (`xoxb-...`).

### Neo4j Aura

From the Aura console, copy:

- Connection URI (looks like `neo4j+s://xxxxx.databases.neo4j.io`)
- Username (typically `neo4j`)
- Password (generated when you created the instance)

## Building and running

```bash
cd sync
go mod tidy
go build -o bin/sync ./cmd/sync

# Required environment variables
export LINEAR_API_KEY=lin_api_...
export SLACK_BOT_TOKEN=xoxb-...
export NEO4J_URI=neo4j+s://xxxxx.databases.neo4j.io
export NEO4J_USER=neo4j
export NEO4J_PASSWORD=...

# Optional
export NEO4J_DATABASE=neo4j                  # defaults to "neo4j"
export QUERIES_DIR=../data-model/queries     # defaults to a relative path

# Optional — embedding + semantic linking (see "Embedding and semantic
# linking" below). Unset EMBEDDING_BASE_URL entirely to skip this stage
# and behave exactly like iteration 1.
export EMBEDDING_BASE_URL=http://localhost:1234/v1   # LM Studio
export EMBEDDING_MODEL=text-embedding-nomic-embed-text-v1.5
export SEMANTIC_LINK_THRESHOLD=0.78          # defaults to 0.78
export SEMANTIC_LINK_TOPK=5                  # defaults to 5

# Run the sync once
./bin/sync \
  --linear-project <linear-project-id> \
  --slack-channel <slack-channel-id> \
  --slack-since-days 30

# Or keep it running for a live demo (see "Live demo mode" below)
./bin/sync --watch --interval 20s \
  --linear-project <linear-project-id> \
  --slack-channel <slack-channel-id>
```

### Finding the IDs

- Linear project ID: open the project in Linear → URL is
  `linear.app/<org>/project/<slug>-<uuid>`. The UUID is the project ID.
  You can also list projects via the Linear API to confirm.
- Slack channel ID: in Slack, right-click the channel → "Copy link". The
  ID is the last path segment (e.g. `C09ABCDEF12`).

## Embedding and semantic linking

A fourth pipeline stage, after the explicit linking pass: embed every
Issue's title and every Message's text through an OpenAI-compatible
`/v1/embeddings` endpoint (`sync/internal/embed`), write the vectors with
`db.create.setNodeVectorProperty` (`embed-issue.cypher`,
`embed-message.cypher`), then run `link-semantic.cypher` — cosine
similarity search over the `message_embedding` vector index, creating a
`:DISCUSSED_IN` edge (`evidence: "semantic_match"`, `confidence:` the
similarity score) for any (issue, thread) pair the explicit pass missed.
An edge the explicit pass already created is never touched — see the
comment in `link-semantic.cypher`.

This is entirely optional: `EMBEDDING_BASE_URL` unset means the stage is
skipped and `orchestrator.Run` behaves exactly like iteration 1. Set it
to a local [LM Studio](https://lmstudio.ai) server
(`http://localhost:1234/v1` once you've loaded a model and started its
server — `lms server start`, or the "Local Server" tab in the app) and
`EMBEDDING_MODEL` to the loaded model's identifier
(`text-embedding-nomic-embed-text-v1.5` for the model this demo is built
around — 768 dimensions, matching `schema.cypher`'s vector indexes).
Embeddings never leave the machine — no cloud provider in the loop.

**Re-embeds everything, every run.** At demo scale (a handful of issues
and messages) this is simpler and safer than tracking what changed, and
it's how edits get picked up without any extra logic. It would not scale
to a large real workspace — see `data-model/README.md`'s "What to watch
out for with externally-generated embeddings" for the production version
of this tradeoff.

**Dimension is locked to the vector index.** `schema.cypher` pins both
vector indexes to 768 dimensions. Swapping `EMBEDDING_MODEL` for a
different-dimension model without updating and recreating the indexes
fails loudly (`Vector index ... has a configured dimensionality of 768,
but the provided vector has dimension N`) — it does not silently corrupt
similarity scores.

**Never point this at the same database as the canonical seed graph.**
Verified live 2026-08-28: the real Linear/Slack workspace mirrors the
canonical demo story closely enough (NEO-10 ≈ NODES-1, etc.) that
embedding both into one database floods the semantic pass with
cross-links between the fictional and real versions of the same issues.
Give the live demo its own database (`NEO4J_DATABASE=livedemo`, created
once via `CREATE DATABASE livedemo` — Enterprise-only) — see
`DEMO-ENV.md` → "Live embedding demo" for the full runbook.

**`SEMANTIC_LINK_THRESHOLD` (default 0.78) is the heuristic the talk is
honest about on stage** — and it doesn't cleanly solve the problem, it
just picks a workable tradeoff. Verified live against real
nomic-embed-text-v1.5 embeddings, twice (2026-08-28): against the
6-issue canonical seed graph in isolation, 0.78 is the only threshold in
a 0.0024-wide window that keeps the intended link (NODES-1 → orphaned
thread, 0.7811) while excluding four false positives (0.7663–0.7788).
Against the real 8-issue workspace (in its own `livedemo` database), the
intended link still forms (NEO-10 → orphaned thread, 0.780) but **the
same 0.78 also lets seven further false positives through** (0.759–0.779)
— the tuned window doesn't generalize to a different corpus. Decision:
ship it as-is and accept the extra links rather than build reranking or
top-1-per-issue logic. If asked why extra links appear on stage, that's
the honest answer, not a bug. Check `data-model/README.md` for the wider
discussion of the threshold tradeoff.

## Live demo mode

`--watch` re-runs the full pipeline (pull → upsert → link → embed →
semantic-link) on a timer instead of once, so a Slack message or Linear
issue posted during the talk gets pulled in automatically without anyone
running a command on stage:

```bash
export NEO4J_DATABASE=livedemo   # NOT the default "neo4j" — see above
./bin/sync --watch --interval 20s \
  --linear-project <linear-project-id> \
  --slack-channel <slack-channel-id>
```

A failed tick (a transient Slack rate limit, a Linear blip, LM Studio not
yet warmed up) is logged and the loop continues at the next interval —
it does not exit. That matters for a live demo: nobody wants to be
restarting a crashed process mid-talk.

**Verify your Slack app's rate limit against `--interval` before relying
on this live**, especially with a short interval. Linear's limits are
generous enough not to worry about (§ Rate limits below), but Slack has
tightened `conversations.history`/`conversations.replies` limits for
non-Marketplace apps in the past, and this demo's Slack app is a fresh
single-workspace bot — not Marketplace-listed. A 429 mid-tick just logs
and retries next interval rather than crashing, but repeated 429s during
a live segment still look bad. Do at least one real timed dry run at
your chosen interval before the talk and watch for `status 429` in the
log; lengthen `--interval` if you see it.

After sync, open Aura Browser or `cypher-shell` and run the agent context
query against a known issue:

```cypher
:param identifier => 'NODES-1'

MATCH (i:Issue {identifier: $identifier})
OPTIONAL MATCH (i)-[d:DISCUSSED_IN]->(t:Thread)
RETURN i.identifier, i.title, count(d) AS discussions
```

If `discussions > 0`, the linking pass worked. If it's zero but you expected
discussions, check that the message text actually contains the identifier
in a regex-extractable form.

## Things to know

### Idempotency

Every stage uses `MERGE` rather than `CREATE`. Re-running the sync after
a partial failure replays cleanly. The third stage (explicit linking) also
uses `MERGE` on the `:DISCUSSED_IN` edge so re-runs don't duplicate
relationships.

### Rate limits

- Linear: 1500 requests / hour for personal tokens. Sync touches the API
  once per page of issues (50 per page), so a 250-issue project is 5
  requests. Plenty of headroom.
- Slack: tighter, especially for `conversations.history` and
  `conversations.replies`. The sync pipeline batches conservatively.
  For demo-scale data you won't hit limits; production sync of a busy
  channel would need backoff.
- Neo4j Aura: no rate limit, but free-tier instances pause after 3 days
  of inactivity. Re-resume from the Aura console.

### Person reconciliation

The `:CREATED` and `:AUTHORED` relationships unify users across Linear
and Slack by email. This works because:

- Linear's `creator { email }` returns the user's email
- Slack's `users.info` returns `profile.email` when the bot token has
  `users:read.email` scope
- Both systems use the same primary email for the same human (usually)

When the emails *don't* match — corporate Linear, personal Slack — the
sync creates two Person nodes for what's actually one human. Iteration 2's
vector-based entity disambiguation can address this; iteration 1 doesn't.

### What's not included

- **Webhooks for live updates.** The sync is batch-only. Linear and Slack
  both have webhook APIs; wiring them up is straightforward but adds
  infrastructure (an HTTPS endpoint, an event queue) that the demo
  doesn't need.
- **Concurrent pulling.** Linear and Slack pulls run sequentially. For
  larger volumes you'd want them in parallel via `errgroup`.
- **Cycle/issue-level webhook reconciliation.** Linear has a "completed
  at" timestamp; we don't use it. The sync re-pulls everything every run.

### Failure modes worth knowing

| Symptom | Cause | Fix |
|---------|-------|-----|
| `verify connectivity: failed to connect` | Aura paused, URI wrong, or password rotated | Re-resume Aura, double-check env vars |
| `linear api returned 401` | Personal API key revoked or wrong | Generate a new one in Linear settings |
| `conversations.history: not_in_channel` | Bot isn't in the Slack channel | Invite the bot to the channel |
| `users.info: missing_scope` | Bot token doesn't have `users:read.email` | Add the scope, reinstall the app |
| Empty discussions after sync | Slack messages don't contain the issue identifiers | Check that the message text names the identifiers exactly as they exist on the Issue nodes in the graph (the linking pass is word-boundary matching against every in-graph identifier — there is no pattern flag) |

## Deployment notes for later

When this moves to a Lambda for production sync:

- The orchestrator stays unchanged. It's pure logic.
- `cmd/sync/main.go` is replaced by a Lambda handler that reads the same
  env vars and calls `orchestrator.Run` directly.
- Secrets move from env vars to AWS Secrets Manager, loaded at cold start.
- `QUERIES_DIR` becomes a path inside the deployment artifact (the
  `data-model/queries/*.cypher` files get bundled into the Lambda zip).
- EventBridge schedule replaces manual invocation.

That's a separate piece of work, not part of this directory.
